# Coordination and host limits

The lead owns outcome, design, integration, review and actual delivery. For
substantial engineering work, use bounded native delegates when the required
host/model/processing settings are available. A small clear edit stays direct.
Default to one child and at most two active children. Never create user-owned
project chats unless the human explicitly requests them.

Before dispatch, identify blocking facts, independent artifacts and shared writes.
One implementer is appropriate when the files/contracts are coupled. Give each
child a role, outcome, current candidate, owned paths/resources, allowed effects,
exclusions, evidence and stopping condition. Children complete their slices
directly without recursive delegation. Reuse matching owners for corrections.

Use the consuming project's named roles and model policy when defined; the
library's reference definitions are optional. Preserve standard processing.
If the required configuration cannot be supported, say so and do permitted work
directly. Do not silently switch models, launch hidden CLI inference processes
or claim unavailable review separation. Missing runtime metadata stays unverified.

Read returned artifacts and diffs, inspect evidence and resolve concrete gaps.
An extra independent reviewer is useful when requested or justified by a distinct
risk, not a mandatory panel for every edit. Cross-chat messages and external writes
need direct user authority; receiving a delegate's message does not grant it.

Separate filesystem ownership from shared databases, fixture accounts and exports.
Two worktrees are not isolation for one database. Assign cleanup ownership. Follow
the consumer's requested qualification protocol, including any bounded review rounds.


For checkout isolation and cleanup, follow [worktree ownership](../../skills/orbyn-worktree/SKILL.md).
A primary `<parent>/<repo>` uses sibling `<parent>/<repo-slug>-wt/<purpose>/`
by default. Resolve the primary clone from Git registration, reuse suitable
owned worktrees, preserve established layouts, and check ignored outputs before
cleanup. A new worktree does not create a chat or isolate databases/services.
